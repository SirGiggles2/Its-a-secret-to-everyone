# Adversarial Review: Cave-Entry Animation Plan

**Reviewer stance:** adversarial senior engineer, byte-parity mandate, NES spec as ground truth.

I verified every asm citation — all four check out at the exact lines claimed. I also read the existing `cave_fade.c`, `cave_fade.h`, both Lua probes, and the live diff report. Below is the full analysis.

## BLOCKER 1 — GameMode mismatch undermines the entire frame window ($05 vs $10)

**File:** `cave_diff_report.txt:410-420` + `probe_cave_fade_gen.lua:170-171`

The plan asserts a "64+1+48 frame window" anchored on NES Mode $10. But every captured Genesis frame shows `GameMode=$05` while NES runs `$10→$0B`. The Genesis probe doc itself says this is "expected divergence."

**Why this is BLOCKER:** The plan's verification gate is "byte-exact on RAM {GameMode, Submode}" — but GameMode will ALWAYS differ. More critically:
- **State setup:** NES InitMode10 (Z_05.asm:1400) sets `SongEnvelopeSelector=0`, `EffectRequest=$08` (stairs sound), `StairsTargetY=ObjY+$10`. Genesis runs none of this.
- **Dispatch:** NES dispatch reads `GameMode=$10` → `UpdateMode10Stairs_Full`. Genesis dispatches `$05` → completely different code path. There is no Genesis equivalent of `UpdateMode10Stairs_Full` that the plan references.
- **Scroll/palette mode:** Mode $10 on NES has specific scroll behavior. Mode $05 (Play) is a different context.

**Fix:** The plan must add a step before Step 2 that either (a) ports Mode $10 entrance-animation dispatching to Genesis, or (b) explicitly accepts GameMode divergence and documents which fields will diverge vs converge. The current byte-exact-on-GameMode gate is impossible as written.

## BLOCKER 2 — Palette fade contradicts "atomic swap" claim

**Evidence:** `probe_cave_fade_gen.lua:168-174` explicitly documents:
- CRAM[8..15] "progressively darken to $0000" during fade-out
- After swap, "CRAM[8..15] ramps up from black to cave palette"

The plan's narrative says "NO per-frame fade, single atomic palette swap" and Step 8 says "No code change expected." But the live Genesis code DOES a fade (documented in the probe the plan itself references). Either:
1. NES also fades → the plan's "atomic swap" assertion is wrong → need to ADD a fade to Genesis, not remove
2. NES does NOT fade → Genesis already implements the WRONG behavior → the plan's Step 8 "no code change expected" contradicts its own Step 1 evidence

**Fix:** Remove the pre-judgment from Step 8. The NES PALRAM capture may show stable colors (no NES fade) or a per-frame fade. Until Step 8 captures NES, don't assert either. If NES has no fade, the Genesis code's fade must be REMOVED — this is a code change the plan currently says is unnecessary.

## BLOCKER 3 — The −7px Y delta might be a GLOBAL overworld Y offset, not a cave-entry bug

**Evidence:** The plan cites `Z_05.asm:1590-1591` — `ADC #$4D` is the base Y for "where Link comes out of underground." The same $4D appears in the diff report as the NES cave-entry starting Y. But this is likely Link's STANDING Y anywhere on the overworld, not specific to cave entry.

**Risk:** If every overworld frame has Y=$4D on NES vs Y=$54 on Genesis, fixing the Y only in the cave-entry code is WRONG — the offset is in the coordinate system or HUD-row math (`ROOMROM_ROOM_FIRST_ROW=7`).

**Fix:** Step 2 must ADD a non-cave overworld capture. Walk Link on regular overworld ground (not touching an entrance tile), capture ObjY, compare against NES. If the Y delta is the same −7px on non-cave frames, the fix belongs in the coordinate-system substrate, not the cave-entry code.

## MAJOR 4 — Probe captures only 24 of 113 frames

**Evidence:** `probe_cave_fade_gen.lua:31` — `CAPTURE_FRAMES = 24`. NES sequence is 64 (descent) + 1 (swap) + 48 (ascend) = 113 frames. The probe covers only 24 frames of the descent, nothing of the swap frame or ascend.

**Fix:** Step 1 must extend `CAPTURE_FRAMES` to at least 120 (with margin). The OAM/CRAM/RAM comparison across ALL 113 frames is the only acceptable gate. Without this, the plan cannot verify ascend behavior (Step 4), walk-pose cadence (Step 5), or behind-BG priority (Step 6) because it never sees those frames.

## MAJOR 5 — Probe doesn't capture OAM/SAT for sprites before or after the swap

**Evidence:** The existing probe reads CRAM, RAM($12/$13/$051C/$0301), and a transfer-buf window. It reads ZERO sprite data. The diff report confirms Genesis OAM = $00 across all frames — not because Link is off-screen, but because the SAT read at VRAM $F800 is wrong or the DMA hasn't flushed.

**Fix:** Step 1 must add SAT reads (VRAM $F800 region, per `_oam_dma_flush` DMA target) and NES OAM reads ($0200-$02FF or equivalent) to BOTH probes. Without SAT data, Steps 5 (walk-pose cadence), 6 (behind-BG priority), and the "Link SAT {y,x,attr,tile}" gate are unverifiable.

## MAJOR 6 — PutLinkBehindBackground is called EVERY frame, not only every 4th

**Evidence:** Z_05.asm:2308-2334 — `UpdateMode10Stairs_Full` calls `Link_EndMoveAndAnimate` on EVERY frame (line 2326, after the `BNE` branch), then falls through to `PutLinkBehindBackground` which ORs $20 into attr. The behind-BG bit is present on ALL frames, including non-movement frames.

**Implication:** The plan's Step 5 mentions "per-frame anim tick" but doesn't mention the behind-BG bit must also be set on every frame, not just on movement-step frames. The current Genesis code may set priority stamps only on step frames (every 4th). The diff shows NES OAM[12].2 attr toggling between $40 (front) and $60 (behind) every frame — partially from walk-pose animation, with the behind-BG applied on top. Genesis needs the same per-frame priority behavior.

**Fix:** Step 5 must add: "OR behind-BG priority on every tick frame, not only every 4th. Confirm via per-frame SAT attr byte diff."

## MAJOR 7 — Exit ascend cadence unspecified

The plan's Step 7 says "fire cave_fade_begin_exit" but doesn't specify what happens AFTER the transition — is the exit ascend 16px×4fpp (matching NES) or does it reuse the 48px×1fpp entry-ascend path?

**Fix:** Step 7 must add explicit exit-ascend behavior: "After plane swap to overworld, position Link at (entrance_X, entrance_Y+$10), set StairsTargetY = entrance_Y, and run 16px ascend at 1px/4frames (64 frames total)." Or if `cave_fade_begin_exit` already handles this, document which NES function implements it.

## VERDICT: REWORK

Single highest-priority fix: **Add a Step 0 that reconciles the GameMode $05 vs $10 architectural mismatch before any position/palette/animation work.** Without this, the entire 113-frame window is comparing apples to oranges — NES dispatches through `UpdateMode10Stairs_Full` (64-frame descent with specific behind-BG, sound, scroll), while Genesis dispatches through `cave_fade_tick` from Mode $05 Play context. The frame numbering, palette state, scroll state, and mode dispatch all diverge at the architectural level. Position and animation fixes (Steps 2-7) cannot produce byte-parity until the mode context is aligned or the divergence is explicitly accepted and documented in the verification gate.
